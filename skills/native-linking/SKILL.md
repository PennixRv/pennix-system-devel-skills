# ELF 链接与加载

先区分编译、链接和装载哪一步失败。查实际链接驱动、目标架构、命令与工件，不以预期构建参数代替真正生效的参数。交叉构建已证实输入和目标身份时，同样适用下面的链接取证；若问题是目标库被宿主库替换，先追实际工具链与搜索路径。

1. **对上符号及输入。** 用链接日志、map 或 `nm`／`readelf` 对照未定义引用、提供者、符号版本及可见性。C 和 C++ 名称、同名输入、静态归档成员和对象文件不是同一证据。考虑当前链接器如何提取归档成员、处理库次序和链接选项；GNU ld 下静态库可能需要放在引用它的对象后。循环依赖先核对结构，不默认使用全量归档或分组。
2. **按装载环境取证。** 用已有错误消息与 ELF 的解释器、`NEEDED`、`SONAME`、`RPATH`、`RUNPATH` 对照实际运行环境和间接依赖；按目标加载器语义解释，不把某个系统的搜索顺序套给所有 ELF。读取 ELF 结构不证明库实际可加载或初始化成功；不要对未知二进制运行 `ldd` 或启动工件。
3. **匹配改动和验证。** 生成的链接命令只能说明现场；修复应落在实际拥有目标和依赖的输入。检查构建日志或工件即可判定时不默认重配，必须运行时先核对目标和授权。若要求比较 PIE、RELRO 或其它加固，核对实际产物和适用目标，不能凭一个编译参数推断全部保护或运行安全。

交付首个失败层、相关输入与有效工件、最小改动、需要补的证据。归档和链接选项查目标链接器，例如 [GNU ld 手册](https://sourceware.org/binutils/docs/ld/Options.html)。
