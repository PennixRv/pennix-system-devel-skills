# 首发行为评测基线

用合成夹具，不用真实项目源码、凭据或运行环境。表中每格是一条独立的自然请求；只把夹具与请求交给被测宿主，不泄露预期入口或判断。A 与 B 使用相同的现有集合、宿主、模型设置和请求；只有 B 可见候选成员。记录实际入口及参考读取路径、关键判断、缺项和副作用；只找到入口文件，或模型自述“已读取”，都不证明实际使用。必需证据不清楚时保留未知。

[`cases.json`](cases.json) 逐条分离输入和判据。`python3 -B evaluations/case.py` 列出用例，指定用例 ID 生成仅含输入的提示，`--rubric <ID>` 仅供审查者读取判据，不能输入被测会话。这些命令只生成文本，不发模型请求。每轮使用新会话并保存实际宿主、模型、候选摘要与隔离身份；依赖未获准时停止验证。比较原始轨迹时，只把可证明实际成功读取的入口或参考标为已读，其他标为未知。轨迹和日志不进入 Git。

每个成员的正例至少应产生一项 A 未提供的、可核实的判断或更准确的停止条件。对照不得误触发、误报缺陷、默认执行命令或夸大静态证据。另用不同项目布局重跑 C、脚本、驱动、用户态和 Zephyr 的正例。下列语义为固定基线；实施时补充最小正文夹具与预期路径，不因评测跑分临时放宽判据。

| 入口 | 正例与判据 | 对照与判据 |
| --- | --- | --- |
| `c-systems` | 审查可移植 C 库的元素个数乘元素大小再分配；核对乘法前的上界、长度单位和失败后的所有权。 | 同样的操作由 C++ 容器和现有安全接口完成；不要套入 C 分配与释放方案。 |
| `cpp-coding-standards` | 审查禁用异常的 C++17 模块中跨作用域保存借用视图；依据实际所有者和 C++17 能力判断，不要求升级标准。 | 纯 C 模块调用持有缓冲区的 API；不触发 C++ 规范。 |
| `cpp-testing` | 已有 GoogleTest/CTest 的交叉工程，目标可编译但无执行器；区分编译、发现与运行，使用已有目标。 | 既有测试显式提供执行器且有运行回执；不把交叉构建笼统标为无法运行，也不下载框架。 |
| `zephyr-foundations` | 应用 `.conf` 希望打开符号，目标域配置却未启用；按实际构建目录核对板卡、合并结果及依赖，不把 DTS overlay 当成配置赋值。 | 同名符号来自 Linux 内核的 defconfig；不建议 `west`，不套用 Zephyr 合并规则。 |
| `linux-kernel-review` | 审查当前提交中释放对象后才同步工作队列的改动；从差异和调用路径证实具体回归，以位置和因果报告。 | 再给正确清理顺序的差异；没有实际回归时不造问题、不发评论、不写评审文件。 |
| `cmake` | 解释两个不同构建目录为什么选了不同 C++ 编译器；核对 preset 继承、工具链及缓存，不自动重新配置。 | 只有 Meson 工程；不将 CMake preset 或缓存假定为事实。 |
| `make` | 改了头文件却没重建；从 `.d`、对象规则和包含路径找缺边，识别生成的 Makefile。 | 目录仅作顺序依赖；目录时间改变而内容依赖不变时不建议强制重编译。 |
| `cross-toolchain` | 目标链接器收到错误架构的库；追真实链接参数、sysroot、目标 ELF 和宿主工具来源。 | 真实问题是目标程序运行时找不到动态解释器；不把链接已通过说成运行已通过。 |
| `gdb` | 现有 core 与现场符号的 Build ID 不一致；先核对工件，不附加进程或换个构建冒充现场。 | 给匹配符号、已有回溯但无法连远端的对照；只分析已有证据，不启动远端。 |
| `elf-abi-compatibility` | 比较两个共享库，源码签名看似相同但公开结构布局变化；分别给源码、ABI 和运行结论。 | 剥离工件只剩动态符号；不能因为符号集合相同就认定 ABI 兼容。 |
| `bash-defensive-patterns` | Bash 批处理在第二个命令失败时留下中间文件；检查错误传播、清理所有权和重跑，不随意加全局严格模式。 | 同样请求的目标解释器是 POSIX `sh`；不建议 `[[ ]]` 或假定 `pipefail`。 |
| `posix-shell-pro` | 同一 `/bin/sh` 脚本须在 dash 和 BusyBox ash 运行；分开判断语言语法、外部工具选项和清理 trap。 | 项目明确要求 Bash 并依赖数组；不擅自移除 Bash 或改 shebang。 |
| `python-system-scripting` | 子进程写入中间工件后超时，重跑会覆盖旧输出；区分直接进程与后代，说明回收和提交边界。 | 审查纯 Python 算法，不启动进程或产生文件；不转向系统脚本工作流。 |
| `embedded-systems` | 裸机 ISR 将缓冲区交给主循环，另有 DMA 还在使用；明确中断与 DMA 的所有权和失败路径，不能凭源码宣称时序达标。 | Zephyr 项目使用其工作队列和设备模型；不套用裸机或 FreeRTOS API。 |
| `linux-driver-lifecycle` | 设计一个具备延迟工作、IRQ 和失败探测的目标树驱动；区分资源释放和并发停机并给验证边界。 | 单问 Linux `CONFIG_*` 最终为何未生效而没有驱动变更；应走配置值的按需参考，不要求改驱动。 |
| `linux-userspace-development` | 服务进程已启动却在完成资源初始化前通知就绪，另有异步关闭回调；核对何时就绪与最后使用者。 | 一次性命令无常驻服务或跨回调生命周期；不引入守护进程、事件循环或服务管理器。 |
| `linux-perf` | 只给两份计数和采样报告且采样事件不同；说明可比较与缺失条件，不把计数等同于根因。 | 权限阻断、事件不可用；不建议以提权或改 sysctl 作为默认动作。 |
| `yocto-recipe-development` | 新 `.bbappend` 加入一个运行时工具；确认目标分支、匹配的 recipe、实际包名和分阶段依赖。 | 仅有 `do_compile` 失败日志；不因看到 `.bb` 就默认改配方，先找失败任务。 |
| `bitbake-debug` | 已构建成功但镜像缺包；直接取镜像 manifest、pkgdata 和包归属参考，不盲目重跑 `do_rootfs`。 | 提供 `do_compile` 日志且错误指向宿主工具；不误认成镜像缺包，不回显完整环境。 |

混合对照：① Yocto 的内核片段未进入最终工件，先确认所选 recipe、任务上下文和工件归属，再在有 Linux 配置证据时读取对应参考；不要启动普通内核全量审查。② Zephyr 交叉构建后的 GDB 符号不匹配，先确认目标和工件身份；不要因看到板卡或工具链就默认重新构建、启动调试或使用 perf。
